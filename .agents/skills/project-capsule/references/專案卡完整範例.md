## 二、「專案紅線」怎麼寫才有用

紅線段是整張卡最值錢的地方。判斷標準只有一個：
**下一次如果不知道這件事，會不會出事？**

好的紅線寫法 —— 有觸發條件、有對策、有一句話證據：

```markdown
- **不要直接改線上那份**，一律改測試站確認後才推正式站。
  8/25 直接改線上導致營業時間顯示錯誤兩小時。
```

沒用的紅線寫法：

```markdown
- 要小心不要出錯
- 注意品質
- 客戶很重視細節
```

這三句沒有告訴下一個人「什麼時候該做什麼」，等於沒寫。

**紅線不是雜物袋。** 一次性的提醒（「這週五要交」）、一般常識（「檔案要備份」）
不要放進來，會把真正重要的規則淹沒。理想的紅線段是 3-6 條。

## 三、改寫 vs 並列：最常犯的錯

專案有新決定時，要**改寫舊的那一行**，不是在下面補一行。

錯誤示範（新舊並列，下一次讀的人不知道該聽誰的）：

```markdown
## 目前定案
- 上線日訂在 9/1。
- 上線日改成 9/8。
- 上線日最終確認為 9/15。
```

正確示範：

```markdown
## 目前定案
- 上線日 9/15，客戶已經跟通路說好，不能延。
```

如果「為什麼改期」很重要，它屬於下面這一段：

```markdown
## 下一次不要做什麼
- 不要再問能不能提前上線。9/1 與 9/8 都因為客戶素材沒到而延過，
  9/15 是客戶自己拍板的日期。
```

## 四、什麼該進卡片、什麼該留日記

| 內容 | 去哪裡 |
|---|---|
| 「這個案子現在卡在金流」 | 卡片 · 還沒做完 |
| 「今天下午三點我把商品頁的字體從 14px 改成 16px」 | 日記 |
| 「客戶說產品照不能自己修圖」 | 卡片 · 專案紅線 |
| 「測試站網址是 test.wangji.example」 | 卡片 · 重要路徑 |
| 完整的錯誤訊息與排查過程 | 日記 |
| 「排查完的結論是套件版本不相容，已改用 3.2 版」 | 卡片 · 目前定案 |
| 後台密碼 | **哪裡都不寫**，用 Windows 認證管理員 |

判斷方式：**這件事一個月後還會影響決定嗎？** 會，就進卡片；
只是當天的操作過程，就留在日記。

## 五、卡片太長時怎麼拆

超過大約 180 行時，同一個資料夾底下開兩個檔：

```text
memory/long-term/專案/王記食品官網改版/
├── CAPSULE.md      ← 只留「目前有效」的狀態，一次讀得完
├── CHANGELOG.md    ← 完整的時間軸歷程
└── DETAILS.md      ← 長篇的操作步驟、事故經過、測試紀錄
```

卡片裡只留一行指路：

```markdown
## 現在做到哪
- （最近五條進展…）
- 更早的歷程見 CHANGELOG.md
```

搬完之後檢查一次：卡片裡剩下的內容，有沒有把關鍵資訊一起搬走了。
搬移不等於刪除，兩邊加起來要跟原本一樣完整。
