# Memory Organizer（日記 → 長期記憶）

> 每輪對話先由 hooks 寫入 `memory/daily/`。這個技能只負責週期性整理，不負責即時記錄。

## Step -1：找出記憶根目錄

1. 若目前專案存在 `memory/README.md`，使用目前專案的 `memory/`。
2. 否則使用 `$HOME/.codex/ai-assistant/memory/`。

同樣地，若目前專案存在 `.ai-assistant/qmd/`，使用專案 runtime；否則使用 `$HOME/.codex/ai-assistant/qmd/`。

## Step 0：確認範圍與保留原始資料

處理多天日記時，一起讀完本次範圍內的 `memory/daily/YYYY-MM-DD.md`，辨識跨日延續的同一事件。

同主題「發現問題 → 修正嘗試 → 最終定案」視為同一事件。長期記憶寫最終定案；中間嘗試只放在來源與證據段。

使用者指定多天時，預設一次讀完整個範圍並合併判斷，不要提議逐日分批；逐日處理會把同一事件拆成重複記憶。

即使只整理一天，遇到「昨天、明天、凌晨、跨日、延續、後續、改回、回滾」或同一專案／路徑線索時，也要讀前一天與後一天的相關段落。

每個候選先建立 `event_key`，優先使用：

```text
任務代號 > 專案名稱 > 檔案路徑 > 人物名稱 > 核心關鍵詞
```

寫入前先輸出事件鏈摘要；缺少最終定案時留在 inbox，不得升級：

```text
[事件鏈摘要]
- event_key：
- 日期範圍：
- 初始狀態：
- 中間嘗試：
- 最終定案：
- 被覆蓋／拒收：
- 證據來源：
```

同一事件出現「改成、改用、改回、回滾、不用、取消、最終、定案、後續、覆蓋」時，必須找到最晚的明確定案。

原始日記 append-only。不得重寫或刪除日記內容。

`journal-stop` 產生的日記標題格式是：

```markdown
## HH:mm:ss [任務或對話] 使用者問題的第一行
```

同一段下面固定有六個欄位：

- `[情境]`：來源、session、turn、cwd、類型與完整使用者原話
- `[動作/決策]`：工具名稱與完整助理最終回覆
- `[結果]`：只表示本輪已結束，不等於任務成功
- `[教訓]`：Hook 不自動推論，整理時才依跨輪證據判定
- `[落地]`：日記與 transcript 證據位置
- `[召回鍵]`：標題、turn 與工具名稱

整理時以整段為一個來源事件，不要只抽其中一句。`[動作/決策]` 裡的助理回覆只是主張；凡是宣稱完成修改、測試、部署或外部操作，都要依 `[落地]`、transcript 或實際檔案重新查證。

## Step 1：找出值得長期保留的內容

優先處理：

- 已確認的人物資料與偏好
- 可以重用的錯誤根因與解法
- 已定案的決策與規則
- 穩定的系統或工具設定
- 專案里程碑與目前狀態

一次性指令輸出、寒暄與尚未確認的推測留在日記，不升級。

遇到同時包含以下四個固定特徵的日記段落，視為 Codex 自動產生專案建議的背景任務，不是使用者本人陳述；整段排除，不建立候選、不升級記憶：

- 第一個非空白標題是 `# Overview`
- 包含 `Generate 0 to 3 hyperpersonalized suggestions`
- 包含 `Recent Codex tasks in this project:`
- 包含 `# Response format`

四個特徵必須全部符合，避免把一般英文使用者訊息誤判為背景任務。舊 daily 仍保留原始證據，不回頭刪改。

若日記或助理訊息宣稱「已更新某檔案」「已完成某設定」，先讀取該目標檔或可觀察狀態驗證；只有文字宣稱、沒有實際結果時，不得寫成已完成的長期事實。

若仍不確定，依序回答：

1. 一個月後還會需要嗎？
2. 有明確證據或使用者確認嗎？
3. 能寫成不依賴本輪上下文的完整句子嗎？

三題只要有一題答「否」，就先不升級；分類不明則放 `memory/inbox/`。

## Step 2：分類

| 內容類型 | 目標分類 |
|---|---|
| 人物偏好/生活/關係 | `memory/long-term/人物/` |
| 環境/服務/架構變更 | `memory/long-term/系統/` |
| 互動規範/流程/安全 | `memory/long-term/規則/` |
| 工具/模型/非機密設定 | `memory/long-term/設定/` |
| 錯誤根因+解法 | `memory/long-term/教訓/錯誤案例/` |
| 可重用做法 | `memory/long-term/教訓/最佳實踐/` |
| 專案里程碑/決策 | `memory/long-term/專案/<專案名>/` |
| 分類不明 | `memory/inbox/` |

**紅線**：不確定就留收件夾，不要強行分類。

## Step 3：寫入分類檔

第一次建立或更新長期記憶前，先完整閱讀
`references/長期記憶完整範例.md`。範例只示範格式，不得把虛構內容複製進正式記憶。

### 3.1 建立前強制搜尋

建立任何新檔前，先搜尋整個 `memory/long-term/`，不可只看預計寫入的分類：

1. 用檔名、人物／專案名稱與關鍵詞搜尋所有 Markdown。
2. 用待寫入內容的自然語句執行 `qmd query ... -c memory-longterm -n 10`。
3. 開啟所有可能相關的候選檔，完整閱讀摘要、有效事實、最後更新、來源與變更紀錄。
4. qmd 可能尚未更新；檔案系統的完整搜尋是最後依據。

先把結果分類，再決定寫入：

| 判斷 | 動作 |
|---|---|
| 完全相同 | 不重複寫入；ledger 記 `skipped_duplicate` |
| 語意相同但文字不同 | 合併成較完整的一條，不並列重述 |
| 同一主題且內容互補 | 更新同一 canonical file，分開寫清適用範圍 |
| 看似相近但目標、決策或適用範圍不同 | 保留為不同記憶，建立關聯，不強行合併 |
| 新內容推翻舊內容 | 依「3.2 錯誤記憶修正」更新既有正式檔 |
| 多檔其實是同一主題 | 選一份 canonical file，合併後封存其他重複檔 |
| 來源互相衝突，無法判斷新舊 | 停止並請使用者確認，不得自行選邊 |
| 搜尋後確定無相關檔案 | 才能建立新檔 |

不要用日期或「新版」「最終版」另建第二份同主題檔案。

### 3.2 錯誤記憶修正

使用者本輪明確更正優先於 qmd 召回與舊記憶，但必須先讓 Hook 把更正寫入 daily，再於下一輪執行整理。

修正 canonical file 時：

1. 從 `摘要`、`事實與證據`、`決策` 等有效區段移除舊說法，改成新說法。
2. 不要讓新舊說法並列成兩個仍有效的事實。
3. 保留原 `建立日期`，更新 `最後更新`。
4. 新增或更新 `## 變更紀錄`，記錄日期、舊說法、新說法、修正原因與 daily 來源。
5. `## 來源` 同時保留原始來源與修正來源。
6. 不重寫、不刪除 daily；daily 是更正前後的原始證據。

若已存在多份互相重複或衝突的長期記憶：

1. 依使用者明確確認、來源品質、內容完整度與更新時間選 canonical file。
2. 把仍有效的內容與來源合併到 canonical file。
3. 將其餘檔案的 `狀態` 改為 `已取代`，補上 `取代者` 與日期。
4. 移到 `memory/archive/replaced/YYYY-MM-DD/<原相對路徑>` 保存，不可留在 `memory/long-term/`。
5. 不得只標成 `已取代` 卻仍留在 qmd 會索引的目錄。

任何移動都算修改檔案數；總修改超過五個檔案時，先列出 canonical 與封存清單並取得確認。

通用新檔案格式：

```markdown
---
description: 什麼時候該想起這份記憶，寫成情境（例如「回報任何數字或下結論的時候」），20-80 字；教訓目錄就是用這一行組出來的
類型: 人物 | 系統 | 規則 | 設定 | 教訓 | 專案 | 否決性提案
狀態: 草稿 | 已驗證 | 穩定版 | 已過時 | 已取代
建立日期: YYYY-MM-DD
最後更新: YYYY-MM-DD
來源: 日記
關聯: []
標籤: [短標籤1, 短標籤2]
---

## 摘要
- 一句話說明

## 事實與證據
- 條目...

## 決策
- 已確認的最終定案；沒有就寫「尚無」。

## 適用範圍
- 何時應套用這份記憶。

## 不適用範圍
- 何時不要套用，避免 AI 過度泛化。

## 變更紀錄
- 沒有更正時可省略；有更正時記錄舊值、新值、原因與來源。

## 來源
- daily/YYYY-MM-DD.md — HH:mm:ss [任務或對話] 標題
```

追加到既有檔案時，合併重複內容、保留較新的最終定案，並更新 frontmatter `最後更新`。同一主題只能有一份仍位於 `memory/long-term/` 的 canonical file。

特殊類型不可只套通用格式後就結束：

- `教訓/錯誤案例/`：必須有問題摘要、錯誤訊息或症狀、發生情境、根因、已驗證解法、預防清單、關聯最佳實踐。
- `教訓/最佳實踐/`：必須有適用情境、標準步驟、驗收條件、常見踩坑、關聯錯誤案例。
- `專案/<專案名>/CAPSULE.md`：由 `project-capsule` 技能負責建立與維護，段落格式以該技能為準（一句話、專案紅線、目前定案、現在做到哪、重要路徑、驗證過什麼、還沒做完、下一次不要做什麼、來源）。整理日記時只把卡片裡已經穩定的結論萃取到其他分類，不要自行改寫卡片格式，也不要另建第二張卡。
- `否決性提案/`：必須有提案、否決日期、否決理由、重新考慮條件、現行替代方案、來源。
- `人物/`：未經確認的推測要明寫「待確認」，不可升成已驗證事實。

## Step 4：標記整理狀態

不要修改日記正文。把本次整理紀錄寫入：

```text
memory/archive/organizer-ledger.jsonl
```

每行記錄來源日記、整理時間與寫入的長期記憶路徑。技能不得自行移動 `daily/`；只有使用者明確要求封存時，才先列出範圍並確認，而且原始內容仍須保留。

每行使用一個 JSON 物件；不要加 Markdown code fence：

```json
{"source":"daily/2026-07-18.md","organized_at":"2026-07-18T20:30:00+08:00","targets":["long-term/規則/推送帳號規則.md"],"result":"updated"}
```

錯誤記憶修正使用 `corrected`，只記欄位名稱，不在 ledger 重複完整個人資料：

```json
{"source":"daily/2026-07-20.md","organized_at":"2026-07-20T20:30:00+08:00","targets":["long-term/人物/自己.md"],"result":"corrected","correction_fields":["飲食偏好"],"archived_duplicates":[]}
```

## Step 4.5：重建教訓目錄

AI 每次開工都會先讀 `memory/long-term/目錄.md`，對照目錄挑出這輪要想起的記憶。目錄只能由這一步重建，不要手改。

1. 列出 `memory/long-term/` 底下所有 `.md`，排除 `README.md`、`分類索引.md`、`目錄.md`，以及 frontmatter `狀態` 是 `已取代` 的檔。
2. 每個檔讀 frontmatter 的 `description`；沒有或寫得不是「什麼時候該想起」的情境，先依內容補寫一句再寫進目錄（這也算修改該檔，更新 `最後更新`）。
3. 整份重寫 `memory/long-term/目錄.md`，格式固定：

```markdown
# 教訓目錄

> 由 memory-organizer 自動重建，不要手改。路徑都相對於 `<這個 memory\long-term 資料夾的完整路徑>`。
> 每行：檔案 ｜ 什麼時候該想起

## 教訓
教訓/最佳實踐/回報要附證據.md ｜ 回報任何數字或下結論的時候
## 規則
...
```

4. 依分類分段（人物、規則、教訓、系統、設定、專案、否決性提案），段內依檔名排序；每行只寫一行，不放全文。
5. 第一行下面的說明要寫入這台電腦上的完整路徑，讓 AI 從任何資料夾開工都找得到檔案。

## Step 5：重建 qmd 索引

```powershell
$runtime = if (Test-Path ".\.ai-assistant\qmd") {
    (Resolve-Path ".\.ai-assistant\qmd").Path
} else {
    "$env:USERPROFILE\.codex\ai-assistant\qmd"
}
$env:XDG_CACHE_HOME = Join-Path $runtime "cache"
$env:XDG_CONFIG_HOME = Join-Path $runtime "config"
$env:QMD_CONFIG_DIR = Join-Path (Join-Path $runtime "config") "qmd"
$env:INDEX_PATH = Join-Path (Join-Path (Join-Path $runtime "cache") "qmd") "index.sqlite"
qmd update
if ($LASTEXITCODE -ne 0) { throw "qmd update failed" }
qmd embed -c memory-longterm
if ($LASTEXITCODE -ne 0) { throw "qmd embed failed" }
qmd status
```

只有整理完成的 `memory-longterm` 會加入 qmd 並建立語意 embedding。`memory/daily/` 是原始整理素材，不直接召回。

若本次包含修正，至少執行兩個 query：

1. 用新說法提問，確認命中 canonical file 並回答新結論。
2. 用舊說法提問，確認結果會明確指出舊說法已不適用，不會把它當成目前事實。

若舊檔仍被查到，先檢查它是否還留在 `memory/long-term/`，修正後重新執行 `qmd update` 與 `qmd embed -c memory-longterm`。

## 紅線清單

- 敏感資訊不進記憶（token/密碼/憑證/私鑰）
- 不刪除或重寫原始日記
- 大批操作（>5 檔）先列清單確認
- 不確定不分類——留收件夾

## 完成前逐項驗收

- [ ] 本次範圍內的日記已全部讀完，跨日同事件已合併判斷
- [ ] 每個候選都有 event_key 與事件鏈摘要，缺少最終定案的內容仍留在 inbox
- [ ] 日記宣稱已完成的事項已讀回實際目標驗證，不把口頭宣稱當成果
- [ ] 建立新檔前已搜尋全部 long-term 與 qmd，並判斷新增／補充／更正／重複
- [ ] 沒有把寒暄、一次性輸出、猜測或敏感資訊升級
- [ ] Codex 自動建議背景任務沒有被當成使用者陳述或長期記憶候選
- [ ] 每個長期記憶都有完整 frontmatter、摘要、證據、適用／不適用範圍與來源
- [ ] 同一主題只有一份 canonical file 留在 long-term，已取代檔案已移出 qmd 索引範圍
- [ ] 修正沒有讓新舊說法同時成為有效事實，且變更紀錄保留修正證據
- [ ] 特殊類型具備自己的必要段落
- [ ] `organizer-ledger.jsonl` 每行都是可解析 JSON，且沒有修改原始日記
- [ ] `qmd update`、`qmd embed -c memory-longterm`、`qmd status` 全部成功
- [ ] 用一個與新記憶相關的問題執行 qmd query，確定能命中正式記憶而不是 README 或分類索引
- [ ] 若有修正，已分別用新舊說法查詢，確認只把新說法當成目前事實
- [ ] `memory/long-term/目錄.md` 已整份重建：每份有效長期記憶剛好一行，已取代的檔不在目錄裡，每行的「什麼時候該想起」都不是空的

## 建議節奏

- **每天**：hooks 自動寫日記，不整理
- **週末**：跑一次 memory-organizer 整理過去 7 天
- **月末**：檢查 `教訓/最佳實踐/` 是否有重複可合併的條目
